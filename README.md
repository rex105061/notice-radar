# 公告雷达 · Notice Radar

> A 股公开公告 → LLM 结构化抽取 → 解读与建议口径（含合规风险标记）

---

## 一、这个工具解决谁的什么问题

**① 谁在痛**
上市公司董秘与证券事务代表每天要处理十几到几十条公告。真正耗时的不是写公告——公告是公司自己发的——而是公告挂网后陆续涌来的机构追问：要判断这条意味着什么、对方会追问什么、口径怎么给才不越界。

**② 现有工具卡在哪**
巨潮、东方财富、Wind 做的是**信息分发**：抓取、推送、全文检索、摘要，回答的是「这条公告**说了什么**」。它们不回答「这条公告**对我意味着**什么」——影响判断、机构会追问什么、对外怎么答、哪句话不能说。

**③ 这个工具把什么变成什么**
把公告原文变成三样东西：**一句话判断**、**买方与卖方各自的追问清单**、**可直接使用的口径草稿（附红线命中标记）**。

人做的事从「**从零起草口径**」变成「**在草稿上判断并签字**」。

### 它明确做不到什么


| 边界 | 说明 |
|---|---|
| 语义层面的软性暗示 | 合规判定只覆盖 6 条**词面**红线（预测性 / 承诺性 / 绝对化 / 比较性 / 投资建议 / 未披露暗示）。「经营稳健」「行业向好」这类软性表述判不出来 |
| 扫描件公告 | 无文本层的 PDF（实测多为律所法律意见书、审计报告）解析为空，无法解读 |
| 超长正文 | 正文超过 8000 字会截断，后文条款可能遗漏 |
| 历史口径一致性 | 没有跨期记忆。同一公司前后两次口径是否一致，本工具判断不了 |
| 投资判断 | 不涉及估值、评级、买卖建议。输出定位是「AI 辅助解读」，不是投研结论 |

## 二、做什么 / 不做什么（MVP 边界）

**做**

| 环节 | 说明 |
|---|---|
| 数据获取 | 抓取 A 股公开公告（巨潮资讯网，交易所指定披露平台） |
| 结构化抽取 | 公司 / 公告类型 / 金额 / 交易主体 / 影响方向 / 关键条款 |
| 解读生成 | 一句话解读 + 机构可能关注点 + 建议对外口径 + 合规风险标记 |
| 交付形态 | 命令行 + 网页展示 |
| 质量证据 | 人工标注评测集 + 四维输出质量评估规范 + badcase 归因 |

**不做**（明确写下，防止范围蔓延）

- 用户系统 / 登录 / 付费
- 港股、美股、多语言
- 回测、估值模型、投资建议
- 自训模型 / 自建向量库

```
└────────┬────────┘
         │
    ┌────┴────┐
    ▼         ▼
 cli.py    app.py (Streamlit)
```

## 五、评测结果（2026-11-11）

在 **8 条人工标注**的真实公告上（覆盖利润分配 / 重大合同 / 股权变动 / 并购重组 / 风险事项 / 业绩报告 六类）：

| 指标 | 结果 | 算法 |
|---|---|---|
| 解读准确率 | **75.0%** | 准确记 1、部分准确记 0.5 |
| 口径可用率 | **87.5%** | 可直接用记 1、改后可用记 0.5 |
| 合规漏报率 | **0.0%** | 人工发现「该标未标」的比例 |

- 逐条明细与计算过程：`eval/评测结果_D8.md`，由 `src/score_eval.py` 自动解析标注表生成
- 失效案例档案：`eval/badcases.md`（按数据层 / 抽取层 / 生成层 / 合规层 / 评分层五类归因）
- **样本量说明**：8 条不足以支撑统计显著性，结论应表述为「在该样本上」而非「准确率为 75%」

> **一个必须说明的发现**：系统内置的「质量分」与人工判断**不相关**。
> 107 条自动评分的平均值 90.9，其中 58% 落在 90 分、21% 落在 100 分，区分度接近零；
> 最低分的三条（中标通知书 67、董事辞职 77、董事离任 82）全是**内容极简单**的公告，
> 说明它衡量的是「公告信息丰度」，而不是「解读质量」。这个维度正在重做。

## 六、云端部署

本项目已适配 Streamlit Community Cloud（免费）：

1. 打开 [share.streamlit.io](https://share.streamlit.io)，用 GitHub 账号登录
2. New app → 选择仓库 `notice-radar` → 分支 `main`
3. **Main file path** 填 `src/app.py`
4. Advanced settings → **Secrets** 填入：
   ```toml
   DEEPSEEK_API_KEY = "sk-你自己的key"
   DEEPSEEK_BASE_URL = "https://api.deepseek.com"
   LLM_MODEL = "deepseek-chat"
   ```
5. Deploy

> 部署后默认是**演示模式**（`ALLOW_LIVE=0`）：只展示已预生成的解读结果，不实时调用模型。
> 这样既避免陌生人消耗 API 额度，也让页面零等待。需要完整体验时本地运行即可。

### 数据怎么保持最新

不需要手动跑脚本。仓库里配了 GitHub Actions 定时任务（`.github/workflows/update.yml`）：

| 项 | 配置 |
|---|---|
| 触发时间 | 每天北京时间 18:10（A 股公告集中在 15:00–20:00 披露） |
| 每天做的事 | 抓近 3 天公告列表 → 补 60 条高价值正文 → 生成 30 条解读 → 提交数据库 |
| 结果 | Streamlit Cloud 检测到仓库变化，自动重新部署 |
| 成本 | GitHub Actions 免费额度 2000 分钟/月，本任务每次约 8 分钟 |

**启用方式（只需一次）**：

1. 仓库 → Settings → Secrets and variables → Actions → **New repository secret**
2. Name 填 `DEEPSEEK_API_KEY`，Value 填你的 key
3. 之后每天自动更新。想立刻跑一次，去 **Actions** 页选「每日更新公告数据」→ **Run workflow**

> 密钥只存在 GitHub Secrets 里，不会出现在代码、日志或输出中。
