# 一、端到端流程是怎么跑通的

整条链路有 7 个环节，每个环节的产物都是下一个环节的输入。

```
① 公告采集  →  ② 分类过滤  →  ③ 正文解析  →  ④ 结构化抽取
                                                    ↓
⑦ 网页呈现  ←  ⑥ 优先级与合规判定  ←  ⑤ 解读生成
```

| 环节 | 做什么 | 产物 | 关键约束 |
|---|---|---|---|
| ① 公告采集 | 巨潮资讯网沪深两市，**逐日**分页拉取 | 代码/简称/标题/日期/PDF 链接 | 跨天查询会被接口静默截断 |
| ② 分类过滤 | 关键词规则，先排噪音再判价值 | 18 个类别 + 是否高价值 | 高价值占比 39%（14,607 / 37,738） |
| ③ 正文解析 | PyMuPDF 提取文本层；网页端支持按需单条抓取 | 纯文本（上限 20,000 字） | 扫描件无解，直接跳过 |
| ④ 结构化抽取 | LLM #1，temperature = 0.1 | 类型/金额/对手方/影响方向/关键条款/不确定性 | **只允许写原文有的** |
| ⑤ 解读生成 | LLM #2，temperature = 0.3 | 一句话判断 + 买卖方追问 + 建议口径 + 合规标记 | **允许判断，但不得越界** |
| ⑥ 优先级判定 | LLM 判级 + 规则兜底，取更严重者 | P0/P1/P2 + 依据 + 建议动作 + 窗口 | 模型会低估担保类，规则兜住 |
| ⑦ 网页呈现 | Streamlit，公网部署 | 搜索 → 列表 → 展开看解读 | 每会话限实时处理 3 条，防额度滥用 |

**一次完整调用约 6 秒**（两次 LLM 往返），单条成本约 0.02 元。

# 二、卡点与解决

按「数据层 / 模型层 / 工程层 / 产品层」分类，共 14 个卡点。

## A. 数据层（6 个）

### A1　接口跨天查询会静默截断 ⚠️ 最隐蔽

**现象**：一次抓 10/23–11/09 共 18 天，返回 6,000 余条，脚本显示"成功"。但按天核验后发现，10/23–10/30 一条都没有。

**根因**：巨潮接口在查询跨度过大时**不报错、不提示**，只返回最近的一部分。分页 total 字段看起来正常，看不出截断。

**解决**：`fetch_notices.py` 增加 `date_range()`，把区间拆成逐天请求。按天后单日数据量暴露出真实分布：三季报高峰单日 3,000–5,400 条，是之前跨天查询看到的 1,000 条的 3–5 倍。

> **教训：增量抓取最大的风险不是"抓失败"，而是"抓成功了但有缺口"。**
> 失败会报错，缺口不会——它安静地进入数据库，然后在某天变成用户的一句"怎么没有这条公告"。

### A2　数据缺口在页面上才被发现

**现象**：用户搜「上海能源」，只到 10/20，没有 10/24 的公告。

**根因**：两次抓取分别是 10/15–10/22 和 11/10–11/12，中间 18 天完全没抓。

**解决**：新增 `missing_workdays()`，`--stats` 时自动检查最近 30 天有没有整天缺失，并直接打印补抓命令。

> **教训：数据完整性需要主动校验，不能靠"我记得抓过"。**

### A3　分类规则漏掉 5 类噪音

**现象**：高价值集里混入大量无解读价值的公告。

**根因**：初版规则凭想象写，没有基于真实数据分布。

**解决**：四轮迭代，逐类剥离（共 1,400 余条）：

| 类别 | 条数 | 为什么该排除 |
|---|---|---|
| 中介机构文件 | 681 | 审计报告、法律意见书，是佐证材料，不是解读对象 |
| 境外治理文件 | 216 | A+H 公司的港交所文件 |
| 个人事务类 | 212 | 独董培训承诺函——**标题含"独立董事"，被误判成人事变动** |
| 程序性提示 | 26 | 「将于某日披露季报」，本身没有信息量 |
| 制度文件 | 若干 | 《提名委员会实施细则》《资金占用管理办法》 |

> **教训：「独立董事」既是高价值信号（辞职/聘任），也是噪音信号（培训/承诺函）。**
> 纯关键词匹配分不清语义，这是这类规则的固有上限——必须承认它，而不是假装能解决。

### A4　抓正文时按文件体积排序，抓回一堆制度文件

**现象**：想给恒顺醋业生成解读，抓回的 6 条里 5 条是《独立董事年报工作制度》。

**根因**：`fetch_body` 按 `adjunct_size ASC` 排序（想优先抓小文件，因为解析成功率高）——而制度文件恰好都很短。

**解决**：改为 `ORDER BY is_high_value DESC, adjunct_size ASC`。

> **教训：优化指标（文件大小）如果和真实目标（内容价值）不一致，优化得越好，偏得越远。**

### A5　扫描件 PDF 解析为空

**现象**：73MB 的法律意见书，`get_text()` 返回空串。

**根因**：无文本层的盖章扫描件。律所出 PDF 时通常不保留文字层。

**解决**：**判断不做 OCR**。核查后发现，未解析的大文件 100% 是审计报告和律所意见书（63–150MB），本来就不是解读对象。改为在分类阶段直接排除，并在页面上给出明确提示。

> **教训：不是所有技术缺口都值得补。判断"这个缺口在不在主路径上"，比补它更重要。**

### A6　分类修好了，但分析仍然跑低价值公告

**现象**：分类规则已把制度文件标为低价值，但分析时它们还在被处理。

**根因**：`pipeline.py` 的候选查询只筛"有正文"，没筛 `is_high_value`。**分类与消费之间断了。**

**解决**：SQL 加 `AND is_high_value = 1`。

> **教训：规则改了不等于生效，要检查所有读取这个字段的地方。**

## B. 模型层（3 个）

### B1　抽取与解读合并会导致"脑补"

**现象**：初版用一次调用同时做抽取和解读，抽取结果的数字开始出现原文没有的内容。

**根因**：两种任务对模型的要求相反——抽取要求"只写原文有的"（低温），解读要求"给出判断"（高温）。合并后模型倾向于把判断当事实。

**解决**：拆成两次调用，抽取 temperature = 0.1，解读 0.3。

> **教训：让模型同时做"记录"和"判断"，它会用判断污染记录。**

### B2　合规标记标错了对象

**现象**：让模型标"哪句话有合规风险"，它把**自己生成的卖方提问**也标成了风险（如「是否构成新的推荐逻辑」被判为投资建议）。

**根因**：prompt 没限定检查范围，模型自由扩大了。

**解决**：明确限定 `compliance_flags` 只检查 `suggested_statement`；另开 `question_caution` 字段，单列"哪些问题不能原样抛给上市公司"。

> **教训：让模型判断 X，必须把 X 的边界说死。** "检查有没有合规风险"和"检查这段口径有没有合规风险"，是两件完全不同的事。

### B3　自评分测错了对象

**现象**：每条解读带一个 0–100 的自评分。跑 107 条后，平均 90.9，58% 落在 90 分、21% 落在 100 分。

**根因**：四个维度全在测"有没有"（字段是否为空、长度是否够），没有一项测"好不好"。更糟的是，最低分的三条是「中标通知书 67」「董事辞职 77」「董事离任 82」——**全是内容极简单的公告**。它衡量的其实是「公告信息丰度」。

**解决**：**放弃自评分**，改为公告优先级判定（详见第三节）。

> **教训：一个指标和它该衡量的东西脱钩后，就不再是评估，而是误导——而且它看起来非常像评估。**

## C. 工程层（3 个）

### C1　`server.enableCORS = false` 让 Streamlit 拒绝启动

**现象**：配置文件里写了这一行，服务起不来，日志只有安全警告。

**解决**：删掉该配置。新版 Streamlit 会因此拒绝启动。

> **教训：配置文件里的"优化项"，可能是新版本的"禁用项"。**

### C2　GitHub Actions 文件推不上去

**现象**：`! [remote rejected] ... refusing to allow an OAuth App to create or update workflow ... without 'workflow' scope`

**根因**：gh 的 OAuth token 缺 `workflow` 权限，且是**整体 push 被拒**（不是只拒该文件）。

**解决**：把 workflow 文件从提交中摘出（`reset --soft` + `restore --staged`），改由用户在网页创建。

> **教训：权限问题会以"文件问题"的面貌出现，先看报错原文再动手。**

### C3　自动任务和人工推送打架

**现象**：Actions 跑了 8 分钟后 push 失败，`! [rejected] main -> main (fetch first)`。

**根因**：那 8 分钟里我推了两次代码，Actions 的本地版本落后。

**解决**：workflow 提交前加 `git pull --rebase origin main`，`if/else` 改为提前 `exit 0`。

> **教训：并发冲突不是 bug，是流程设计缺陷——机器和人不能同时改同一个仓库。**

## D. 产品层（2 个）

### D1　页面查不到任何公司

**现象**：部署后搜任何公司都空。

**根因**：数据库是 10/15–10/22 的，页面默认查「近 7 天」（11/05 之后）——两天完全错开。

**解决**：时间范围默认改为「全部」；查不到时明确显示数据库覆盖区间和四种可能原因。

> **教训：默认值必须适配真实数据状态，而不是"一般情况"。**

### D2　用户以为 PDF 读不了

**现象**：大量公告提示"没有可解析的正文"，用户判断"这个雷达对 PDF 公告就没用了"，提出装 OCR 插件。

**根因**：核查后发现——**97% 的公告不是解析失败，是根本没下载过**。库里 37,738 条公告只有 306 条抓了正文，剩下全部只有 PDF 链接。

**解决**：改为**按需抓取**——点开哪条，现场下载解析哪条，结果写回数据库。

> **教训：用户的归因可能是错的，但用户的痛感是真的。**
> 他说"PDF 读不了"，实际是"没有内容"；他要"装 OCR"，实际要的是"点开能看到东西"。**先查数据，再接受结论。**

## E. 一个非技术卡点

**现象**：用户在 GitHub 网页上把 README 的「解读准确率 75.0%」改成了「90.0%」。

**为什么必须拦**：75.0% 由标注表和脚本算出，任何人 clone 后跑一遍就是 75%。数字对不上比数字低危险得多，且会摧毁整个项目「我知道自己哪里会错」的叙事。

**解决**：给出两条正确路径——改回去，或补标让数字自然上去。用户选择补标，样本从 8 条扩到 12 条，算出真实值 87.5%。

> **教训：可复现是数据的底线。** 只要脚本在仓库里，数字就必须能被别人算出来。

# 三、关键调整与取舍

## 取舍 1　自评分 → 公告优先级（最重要的一次转向）

**原设计**：每条解读带一个 0–100 的质量分。

**为什么放弃**：见 B3。这个分数回答的问题没人问——**用户不关心「AI 输出得多好」，只关心「几十条公告里我该先处理哪条」**。

**替代方案**：P0 今日必处理 / P1 三日内准备 / P2 存档即可，附判定依据与具体行动建议。

**设计要点**：模型判级 + 规则兜底，**取更严重者**。实测中「为子公司担保 1.7 亿」模型判 P2，规则按类别拉到 P1——模型容易把日常担保和行政处罚看成同量级。

**质量控制没有消失**：0–100 分仍在计算、仍落库，但**不再对用户展示**，只用于批量跑批时发现异常（字段为空、数字对不上原文）。

> 这次转向的价值不在功能，在于**承认自己设计错了，并且改得比原来更好用**。

## 取舍 2　不做 OCR

放弃了一类能力，换来的是把精力放在主路径上。

**判断依据**：未解析的大文件 100% 是中介机构佐证材料，不是 IR 的解读对象。投入 OCR 的 ROI 接近零。

## 取舍 3　抽取与解读拆成两次调用

成本翻倍（每条 2 次 LLM 往返），换来的是抽取结果不再出现幻觉数字。

## 取舍 4　公网部署默认开启实时分析，但配额 3 条

**为什么不关死**：关掉之后页面只能看预生成结果，演示价值减半。
**为什么限 3 条**：防止陌生人连续刷、把 API 额度耗光。

## 取舍 5　评测样本 8 条 → 12 条，但没改数字

发现数据被改动后，没有选择"改回 75%"或"默认接受 90%"，而是补标 4 条重新计算。

**结果可能更好也可能更差**——实际算出 87.5%，比 75% 高，比 90% 低。**这个数字是算出来的，不是想要出来的。**

# 五、三条经验教训

**1. 「成功了但有缺口」比「失败了」更危险。**
接口静默截断、抓取漏日、分类漏项——这些都不报错。它们安静地进入系统，然后在某天变成用户的一句"怎么没有这条"。所以：**数据完整性要主动校验，不能靠"我记得抓过"。**

**2. 指标一旦和目标脱钩，就从评估变成误导。**
质量分测的是信息丰度，不是解读质量；抓正文按体积排序，优化的是解析成功率，不是内容价值。两者都在"正确地做错事"。

**3. 承认错了，比做得更多更能建立可信度。**
放弃自评分、承认扫描件读不了、把 75% 改回可复现的真实数字——这些动作都不增加功能，但让「我知道它哪里会错」这句话变得可信。
